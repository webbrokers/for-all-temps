# memory/memory_agents.md

## Что это

Каноническая матрица агентов.
Если где-то в других файлах роль агента описана иначе, правильной считается логика из этого файла.

## Статус сейчас

- Джон усилен до роли Chief Manager / Architect / Orchestrator.
- Бэн закреплён как единственный `task-owner`.
- Роль `task-manager` архивирована и больше не используется как активная.
- Феликс доведён до полноценной финансово-операционной роли.
- Рабочие файлы субагентов выровнены по единому шаблону ответственности.

## Матрица ролей

| Агент | Главная роль | Когда подключать | Что должен вернуть |
| --- | --- | --- | --- |
| Джон | Chief Manager / Architect / Orchestrator | Всегда как главный вход | Решение, план, делегирование, сборка результата |
| Бэн | `task-owner` / decomposition / control | Большие и многосоставные задачи | План работ, очередность, контрольные точки, status |
| Кент | coding / implementation / debug | Когда задача уже понятна и надо делать | Патч, тесты, техрезультат, риски |
| Ева | GPU / video / ComfyUI / RunPod | Видео, рендер, media pipeline, GPU infra | Настройки, прогресс, артефакты, техстатус |
| Гений | research / strategy / comparison | Когда нужны варианты и глубокая оценка | Сравнение вариантов, рекомендации, вывод |
| Гермес | Telegram observer / ops | Telegram, роутинг, логи, сбои, наблюдение | Инцидент, лог, гипотезы, статус |
| Ник | SEO / content / structure | SEO, посадочные, контентная архитектура | Семантика, структура, рекомендации, тексты |
| Феликс | finance / budget / unit economics | Бюджеты, расходы, модели, закупки, цены | Расчёт, таблица допущений, риски, рекомендации |

## Делегирование: кто за что отвечает

### Джон

Джон отвечает за:
- приём задачи от пользователя;
- архитектурное понимание;
- выбор исполнителя;
- границы работ;
- чтение логов субагентов;
- контроль памяти;
- финальную сборку ответа.

Джон не должен забирать у субагентов их профильную работу без необходимости.

### Бэн

Бэн — единственный владелец роли `task-owner`.

Он отвечает за:
- декомпозицию;
- выделение этапов;
- контроль очередности;
- фиксацию зависимостей;
- сигнал, когда задачу пора передавать Кенту / Еве / другому агенту;
- короткий статус для Джона.

### Кент

Кент отвечает за:
- реализацию;
- исправления;
- патчи;
- технические тесты;
- аккуратную передачу результатов обратно Джону.

### Ева

Ева отвечает за:
- GPU;
- ComfyUI;
- RunPod;
- видео и media pipeline;
- артефакты и техпроверку таких пайплайнов.

### Гений

Гений отвечает за:
- исследование;
- сбор альтернатив;
- trade-offs;
- объяснение, какой путь лучше и почему.

### Гермес

Гермес отвечает за:
- Telegram-наблюдение;
- инциденты;
- проблемы ответов агента;
- маршрутизацию и операционные логи;
- мониторинг сбоев и отклонений.

### Ник

Ник отвечает за:
- SEO;
- контентную архитектуру;
- структуру страниц;
- семантику;
- рекомендации по контенту и видимости.

### Феликс

Феликс отвечает за:
- бюджетирование;
- оценку стоимости моделей;
- unit economics;
- финансовые риски;
- сравнение расходов по провайдерам, сценариям и конфигурациям.

## Архив ролей

### task-manager

Статус: архив.

Решение:
- роль не дублируется;
- её функции перенесены в Бэна;
- новые задачи на `task-manager` не ставятся;
- при старых упоминаниях читать это как Бэн / `task-owner`.

## Канон по входу в задачу

Перед стартом субагент должен знать:
- цель;
- что считается результатом;
- границы;
- нужные файлы памяти;
- куда писать прогресс;
- какой формат ответа вернуть Джону.

## Канон по логам

Каждый нетривиальный запуск субагента должен иметь `logs/tasks/<task-name>.md`.

Минимум в логе:
- задача;
- текущий статус;
- что уже сделано;
- что мешает;
- что нужно обновить в памяти;
- следующий шаг.

## Чему доучить агентов

### Бэн

- лучше чувствовать зависимости между задачами;
- заранее выделять блокеры;
- различать, когда нужен Кент, а когда Ева или Гений;
- писать короткие статусы для Джона без лишней воды.

### Кент

- давать более чистую handoff-структуру: что изменил, как проверил, что осталось;
- заранее учитывать влияние на память и документацию;
- аккуратно оформлять технические риски и rollback points.

### Ева

- вести более жёсткий operational log по GPU / RunPod / ComfyUI;
- фиксировать контрольные точки пайплайна;
- писать, какие артефакты смотреть Джону первыми.

### Гений

- заканчивать исследование более прикладным выводом;
- давать decision memo, а не только обзор;
- явно фиксировать лучший вариант и условия выбора.

### Гермес

- лучше оформлять инциденты;
- разделять симптом, гипотезу, подтверждение и следующий шаг;
- указывать, когда проблема уже требует эскалации к Кенту или Джону.

### Ник

- теснее связывать SEO-рекомендации с продуктовой целью;
- указывать приоритеты;
- различать быстрые правки и длинные контентные инициативы.

### Феликс

- работать не только как “про деньги вообще”, а как операционный финансовый аналитик;
- считать стоимость сценариев по моделям, токенам, инфраструктуре и людям;
- давать не только цифры, но и управленческие выводы;
- указывать, где можно экономить без потери качества.

## Какие файлы читать агентам

- Всем: `MEMORY.md`, `memory/INDEX.md`.
- По своей специализации: тематический файл из `memory/*.md`.
- При активной задаче: соответствующий `logs/tasks/*.md`.

Если тема про ComfyUI / RunPod / GPU, первым читать `memory/runpod_comfyui_guide.md`.
